## PRIMARY OBJECTIVE

Connect the existing Capital Guardian to Falcon's existing **signal authorization path** so that a proposed trade cannot become an authorized/live signal unless the Capital Guardian explicitly permits it.

The Guardian must become a **hard safety gate**.

Do NOT redesign Falcon's strategies, indicators, Captain logic, execution lifecycle, or position sizing.

# 2. GUARDIAN MUST RUN ON EVERY CAPITAL-RESERVING AUTHORIZATION PATH

For every path capable of producing a trade that could become:

* PENDING
* OPEN
* FILLED

the Capital Guardian must be evaluated before authorization.

A signal must NOT be authorized if Guardian returns:

* `allowed = false`
* Guardian state = `HALTED`
* Guardian evaluation raises an exception
* required risk inputs are missing
* monetary risk cannot be calculated
* active capital cannot be determined
* existing exposure cannot be determined
* any Guardian dependency is unavailable

All such cases must **fail closed**.

Never convert a Guardian failure into:

* WAIT
* reduced-risk trade
* guessed risk
* fallback monetaryRisk
* bypass
* "allow anyway"

# 5. CONCURRENCY / RACE CONDITION MUST BE ANALYZED BEFORE IMPLEMENTATION

This is critical.

A simple sequence like:

```text
Request A → Guardian sees 2 trades → ALLOW
Request B → Guardian sees 2 trades → ALLOW
Request A → creates trade
Request B → creates trade
```

could produce 4 simultaneous trades.

That would violate the Phase 3 invariant.

Therefore inspect the existing transaction and persistence architecture and determine how authorization can safely prevent this race.

Investigate:

* SQLAlchemy transaction boundaries
* PostgreSQL transaction behavior
* existing repository transactions
* whether row-level locks are already used
* whether the application can run multiple Fly.io instances/processes
* whether authorization and trade creation occur in the same transaction
* whether an existing lock/reservation mechanism can be reused

### Do NOT invent an unsafe locking mechanism.

If true atomic authorization + reservation is possible using existing infrastructure, implement it.

If it requires a schema change, STOP and report that a migration is required rather than silently creating one.

If cross-instance concurrency cannot be safely guaranteed with the current schema/architecture, document the limitation and implement the safest fail-closed behavior possible.

Do not claim the 3-trade guarantee is race-safe unless the implementation actually proves it.


# 7. THREE-TRADE LIMIT

The Guardian remains authoritative.

Maximum:

```text
3 simultaneous capital-reserving trades
```

Count:

* PENDING
* OPEN
* FILLED

Exclude:

* CLOSED
* EXPIRED
* INVALIDATED

Do not create a second independent trade-counting implementation.

Use the Phase 3 Guardian.

---

# 8. CAPITAL PRESERVATION

The Phase 3 invariant remains unchanged:

```text
existing worst-case loss
+
proposed worst-case loss
<
active trading capital
```

Strict inequality must remain.

Therefore:

```text
aggregate == active capital → REJECT
aggregate > active capital → REJECT
aggregate < active capital → potentially ALLOW
```

Protected profit is never included.

Do not introduce a percentage-risk limit.

Do not introduce:

* 1%
* 2%
* 5%
* Kelly
* martingale
* fixed fractional risk
* arbitrary drawdown percentages
